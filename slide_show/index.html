Dev vs prod

One codebase. Two lives.

settings/base.py

Shared

Apps, database, auth, static files: everything both worlds agree on.

settings/development.py

Forgiving

DEBUG on. Emails print to the console. Static files served straight from disk.

settings/production.py

Strict

DEBUG off. Secrets required. HTTPS everywhere. Compressed, cache-forever static files.

Same code on every machine. Only one variable changes: DJANGO_SETTINGS_MODULE

[8:15 → 9:15] Split settings.py into a package: base, development, production. Development and production each import base and override what differs. Production is strict on purpose: if the secret key or allowed hosts are missing it refuses to start, which is much better than starting insecurely.
Environment variables

Code goes in git. Secrets don't.

.env stays on the server

Database passwords, the secret key, the hostnames. Never committed.

.env.example goes in git

The same keys with no values: a checklist for the next server.

The real environment wins

python-dotenv never overrides a variable that's already set.

.env.example

DJANGO_SETTINGS_MODULE=app.settings.production
DJANGO_SECRET_KEY=change-me
ALLOWED_HOSTS=pycon.za
CSRF_TRUSTED_ORIGINS=https://pycon.za
DB_NAME=pycon
DB_USER=pycon
DB_PASSWORD=
DB_HOST=127.0.0.1
Lesson learnedThe app and Postgres share a server, so it's 127.0.0.1, not the server's network IP.
[9:15 → 10:15] Three rules. The .env never goes in git. A .env.example with empty values does. And real environment variables beat the file, so your platform or CI can override anything. The sticky note is a real mistake from preparing this talk: I pointed DB_HOST at the server's own network address and Postgres rejected it. More of those in the museum later.

Stop 1 · The server

Start with a fresh Ubuntu VM

Any provider

A cloud VM, a box under your desk, or a VM on your laptop. This talk used one on a laptop.

Start small

A couple of CPUs and a few GB of RAM run a Django site and its database comfortably.

Keys, not passwords

Log in with an SSH key. Use a normal user with sudo, not root.

Choose a supported LTS

Newest isn't always best: some tools take a while to support a brand-new Ubuntu release.

[10:35 → 11:20] Any VM with Ubuntu. Mine ran in UTM on my MacBook, which is a great way to rehearse a deploy for free. One real lesson: I started on the very newest Ubuntu, and some of the panel's tools didn't support it yet. Pick the LTS your tools support.

Stop 3 · The database

Who's allowed to knock?

App → database: localhost

Nothing on the internet needs to reach Postgres. Keep it that way.

Laptop → database: SSH tunnel

DBeaver can connect through SSH. No database port opened at all.

Must open 5432? Be picky

One IP address, real passwords (scram-sha-256), a firewall rule. And replace "trust".

[13:50 → 14:50] This file decides who may connect, from where, and how they prove it. The defaults trust every connection from inside the server; tighten that once your app has its password. For your own GUI, an SSH tunnel beats opening port 5432. I tried both while preparing; the tunnel worked first time.
Stop 4 · Python

Your Python, not the system's

Install the exact version your app needs, next to the one Ubuntu uses for itself. Every project then gets its own virtual environment.

[14:50 → 15:30] Never pip install into the system Python; Ubuntu needs it for its own tools. Install your version alongside and give each project a virtualenv. Note the warning in the app store: the panel is moving this into Website → Python Project, which is what we use next.

Stop 6 · The app server

gunicorn: where your Python actually runs

runserver is for dev

gunicorn starts several Python workers and keeps them busy.

Private port

It listens on 127.0.0.1:8010. Only nginx talks to it.

Its own user

Runs as www, never root.

[16:10 → 17:10] The project form is gunicorn configuration with a UI: framework, start mode, port, and the user it runs as. Two choices matter most: a private port only nginx can reach, and a non-root user, so a bug in your app can't take over the server.

[18:10 → 19:00] collectstatic with WhiteNoise's storage gives every file a content hash in its name and pre-compresses it. Because the name changes whenever the content does, browsers can cache it for a year and never serve a stale file. Our 33 KB stylesheet goes over the wire as 5.6 KB.
Stop 7 · Keep it alive

systemd: the babysitter

User=www

Never run your app as root

--bind 127.0.0.1

Only nginx can reach it

Restart=always

Crashes heal themselves

LogsDirectory=

Logs get a home (ours didn't)

WantedBy=…

Starts again after a reboot

[19:00 → 20:00] systemd is Ubuntu's process manager. Fifteen lines turn gunicorn into a service that starts on boot and restarts when it crashes. The LogsDirectory line exists because my first version pointed logs at a folder that didn't exist; gunicorn crashed instantly, and systemd faithfully restarted it thirty-six times.
Stop 8 · Domain & web server

nginx owns the front door

Which names this site answers to

Pass every request on to gunicorn

Serve uploads straight from disk

[20:00 → 21:00] A site in the panel is an nginx server block. It answers for pycon.za, proxies everything to gunicorn on 8010, and serves user uploads from disk. Point your DNS A record at the server's IP. I used a hosts-file entry, because pycon.za only exists on my laptop. One header in that proxy config cost me an hour; it's in the museum.
Stop 9 · HTTPS

The padlock, two ways

Public domain → Let's Encrypt

Free certificates that renew themselves. One click in the panel, as long as the internet can reach your domain.

Private domain → your own CA

mkcert creates a certificate authority that only your laptop trusts. That's how pycon.za got its padlock here.

Force HTTPS: on HSTS: start with a short max-age Certificates expire: let a robot renew them
[21:00 → 22:00] For a real domain: Let's Encrypt, built into the panel, renewed automatically. It needs the internet to reach your domain to prove you own it. For a private or rehearsal domain like my pycon.za, Let's Encrypt can't help. mkcert makes a tiny certificate authority that only your machine trusts. Either way, turn on Force HTTPS.

The museum of things that broke

Real errors from building this talk

Exhibit 01
DNS_PROBE_FINISHED_NXDOMAIN

The name pointed nowhere yet. Add the DNS record (or hosts entry).

Exhibit 02
ERR_CERT_AUTHORITY_INVALID

A certificate from a CA the browser didn't trust. Trust the CA, or use Let's Encrypt.

Exhibit 03
Connection refused :5432

Postgres only listened on localhost. Usually exactly what you want.

Exhibit 04
no pg_hba.conf entry for host

The app called the server by its network address. Use 127.0.0.1.

Exhibit 05
'/var/log/gunicorn/…' isn't writable

The log folder didn't exist. 36 restarts later… LogsDirectory= fixed it.

Exhibit 06
ERR_TOO_MANY_REDIRECTS

Django didn't know nginx had already done HTTPS. Send X-Forwarded-Proto.

Exhibit 07
Missing staticfiles manifest entry

The built CSS was git-ignored, so it never arrived. Build it, then deploy it.

Exhibit 08
Release file is not valid yet

The VM's clock was 14 hours behind after the laptop slept. Keep time sync on.

[22:30 → 25:00] Every one of these happened while I prepared this talk, on this exact deployment. Step through them quickly; the point is that each one lives at one stop on our route. 01 and 02 are DNS and HTTPS. 03 and 04 are the database door. 05 is systemd. 06 is the proxy header: nginx speaks HTTPS to the browser but plain HTTP to gunicorn, so Django kept redirecting to HTTPS forever. 07 is git-ignored build output. 08: my VM slept with my laptop, woke up fourteen hours in the past, and apt refused to update. If you know the route, you know where to look.

Take this home

The production checklist

  • Settings split: base, development, production
  • Secrets in the environment, never in git
  • DEBUG off, ALLOWED_HOSTS set
  • Database only reachable from inside
  • gunicorn on 127.0.0.1, behind nginx
  • systemd restarts it, and starts it on boot
  • HTTPS forced, certificates auto-renew
  • Static files fingerprinted and compressed
  • One deploy script, run by CI
  • Backups, and you've tested a restore
[27:15 → 28:00] Photograph this slide. If you can tick all ten, you have a production deployment. Notice none of them mention a cloud provider. The last one is the one everybody skips: a backup you've never restored is a hope, not a backup.
